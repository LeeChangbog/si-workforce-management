# 업무 규칙과 구현 경계

Flyway V1/V2는 PK·FK·UK·행 단위 CHECK와 기준 코드를 구현합니다. 아래 교차 테이블 및 권한·동시성 규칙은 기능 구현 시 서비스 트랜잭션에서 검증해야 합니다. 현재 홈 화면은 조회용 기동 확인 범위입니다.

## BR01

사번은 서버에서 동시성에 안전하게 자동 부여한다. 로그인ID는 DB UNIQUE와 가입 화면 중복 검사로 보장한다.

구현 책임: sequence/identity 또는 채번 트랜잭션, UK, application

## BR02

사원구분 DEV는 개발직원에만, NONDEV는 비개발직원에만 정확히 하나 존재한다. 평가구분도 세 하위유형 중 정확히 하나와 일치한다.

구현 책임: 상위/하위 PK-FK, discriminator check, transaction or trigger

## BR03

비개발직원의 소속부서는 마케팅·경영관리·연구개발로 관리한다. 개발직원의 기술등급은 구분 가능한 코드값으로 관리하되 등급 체계는 팀 가정으로 별도 명시한다.

구현 책임: check or domain, application

## BR04

프로젝트참여는 프로젝트·개발직원 조합당 하나이다. 실제 투입 기간과 직무는 직무수행이력으로 반복 기록하며 같은 직무의 동일 기간 중복을 금지한다.

구현 책임: UK, interval validation

## BR05

직무수행이력의 시작일은 종료일 이하이며 프로젝트 시작일 이전 투입을 금지한다. 프로젝트 종료일이 확정되면 투입 종료일은 그 종료일 이하여야 한다.

구현 책임: row CHECK, related-row transaction/trigger

## BR06

현재·과거 시점의 참여자와 직무는 조회일이 투입 기간 안에 포함되는 직무수행이력을 기준으로 판정한다. 경력 기간 합산 시 겹치는 기간을 중복 계산하지 않는다.

구현 책임: query/application

## BR07

경영진 조회 권한은 사원권한으로 부여하고 일반직원의 타인 상세정보 조회를 서버에서 차단한다.

구현 책임: authorization/application

## BR08

평가일은 미작성·작성 중에는 NULL 가능하고 완료 상태이면 필수이다. 프로젝트 종료 시점의 평가라는 기준에 맞게 종료일이 확정된 프로젝트에 대해서만 완료 처리한다.

구현 책임: status-date CHECK, related-row validation

## BR09

피평가자는 해당 프로젝트 참여자이다. 고객 평가자는 프로젝트 발주처의 고객담당자이며, 의뢰PM참여번호의 개발자는 같은 프로젝트에서 PM 직무를 수행한 참여자여야 한다.

구현 책임: FK and related-row transaction/trigger

## BR10

고객평가는 의뢰일시를 기록하고 PM의 회사 보고가 완료되면 보고일시를 기록한다. 의뢰PM이 보고도 주관한다고 가정한다. 보고일시는 의뢰일시 이전일 수 없다.

구현 책임: row CHECK, workflow/application

## BR11

동료 평가자와 피평가자는 같은 프로젝트 참여자이며 서로 다른 직원이다. PM 평가자는 해당 프로젝트에서 PM 직무를 수행한 참여자이다.

구현 책임: FK and related-row transaction/trigger

## BR12

평가상세는 평가·항목당 하나이다. 업무수행과 커뮤니케이션 항목을 초기 적재하고 완료 평가에는 두 항목의 평점·내용을 모두 요구한다. 평점 범위는 제출 정의서에서 한 가지 척도로 확정한다.

구현 책임: composite PK, lookup data, completion validation

## BR13

휴가정책은 종류별 유효기간이 겹치지 않아야 한다. 한도단위는 DAY/HOUR/MINUTE 중 하나로 한도량의 단위를 명시한다. 정책의 일수 산정 방식을 기준으로 신청분을 산출하고 모든 부여·사용·신청 원장은 분으로 저장한다. 일/시간 한도를 분으로 바꿀 때 적용할 근무시간 기준은 정책설명에 명시한다. 법정 상세 산식은 현재 범위에서 확장하지 않는다.

구현 책임: interval validation, application

## BR14

휴가 시작은 종료보다 이르고 신청분·부여분·사용분은 양수이다. 승인 연차에만 연차사용내역을 생성하며 신청자와 연차 부여 대상 사원이 같아야 한다.

구현 책임: CHECK, FK and transaction/trigger

## BR15

승인·차감은 하나의 트랜잭션으로 처리하고 만료·잔여량을 잠금 하에 검사한다. 취소 시 사용내역을 삭제하지 않고 취소 여부/시각을 기록하여 잔여량 계산에서 제외한다.

구현 책임: transaction + row locking

## BR16

휴가와 프로젝트의 직접 FK를 추가하지 않는다. 휴가 신청자→개발직원→프로젝트참여→직무수행이력의 기간 교차로 업무 공백을 조회한다.

구현 책임: query

## BR17

사원 수 100명, 개발자 70명, 월평균 프로젝트 10개는 초기 업무 규모이며 고정 CHECK/행 수 제한을 만들지 않는다.

구현 책임: seed data assumption

## BR18 — 정보 차단벽: 발주처 경쟁 관계

`client_competition`은 발주처 간 셀프 M:N을 해소하는 교차 엔티티다. 기준발주처번호와 경쟁발주처번호를 복합 PK이자 각각 발주처의 FK로 사용한다. 두 관계 `경쟁기준`, `경쟁상대`는 식별 관계이며, 각각 발주처 1개를 필수 참조하고 발주처 하나는 해당 역할의 경쟁 관계를 0..N개 가질 수 있다. 기존 엔티티·관계는 변경하지 않는다.

`client_id_a < client_id_b`로 자기 자신과의 경쟁 및 역방향 중복을 금지한다. 이는 저장 방향을 정하는 규칙이며 경쟁의 의미는 양방향이다. 등록일·해제일은 양끝을 포함하고, 해제일 NULL은 종료일이 정해지지 않은 유효 관계다. 해제일은 등록일 이전일 수 없다. PK가 발주처 쌍이므로 같은 쌍의 여러 유효기간을 별도 행으로 저장하는 재등록 이력은 이번 모델의 범위에 포함하지 않는다.

구현 책임: composite PK, FK 2개, NOT NULL, row CHECK 2개

## BR19 — 경쟁 프로젝트 동시 투입 탐지

한 개발자가 여러 프로젝트에 기간이 겹쳐 참여하는 것은 허용한다. 다음 조건을 모두 만족하는 두 직무수행이력의 조합만 위반이다.

1. 두 프로젝트의 발주처가 저장된 경쟁 관계 쌍이다.
2. 두 참여의 사번이 같다.
3. `A.assigned_from <= B.assigned_to AND B.assigned_from <= A.assigned_to`이다.
4. 두 투입기간의 교집합이 경쟁 관계의 등록일~해제일(NULL이면 무기한)과 하루 이상 겹친다.

DATE 경계일이 같은 경우도 하루의 겹침이다. 현재 해제된 관계라도 과거 유효기간 중 발생한 위반은 조회한다. 경쟁 관계가 아닌 발주처, 같은 발주처의 프로젝트, 다른 직원, 서로 겹치지 않는 투입, 경쟁 등록 전·해제 후의 겹침은 이 규칙의 위반이 아니다. 여러 행을 비교하므로 단일 행 CHECK나 전체 동시 투입을 금지하는 제약을 추가하지 않는다.

대표 조회 SQL은 `src/main/resources/db/queries/client_competition_violations.sql`이다. 사용자 명세에 따라 `overlap_from/to`는 두 투입기간끼리의 교집합을 출력한다. 경쟁 관계 유효기간은 WHERE에서 위반 여부를 판정하며, 출력 기간을 그 유효기간으로 잘라 표시하는 열은 추가하지 않는다. 출력의 한 행은 직무수행이력 두 행의 조합이다. 여러 직무 이력이 있으면 같은 직원·프로젝트 쌍도 여러 행이 될 수 있으며 임의의 DISTINCT로 합치지 않는다. A/B 방향은 발주처번호로만 결정하므로 프로젝트번호·이력번호의 대소 조건을 추가하지 않는다.

구현 책임: multi-table query/application

## BR20 — 등록 사전 경고와 조회 권한

직무수행이력 등록·수정 시 신청한 개발자, 프로젝트의 발주처, 투입기간을 기존 이력·경쟁 관계와 비교하고 위반 예정 건을 사전 경고한다. 자신의 수정 대상 이력은 비교에서 제외하며, 경쟁 관계 유효기간도 함께 검사한다. 경고는 모든 중복 투입을 DB에서 금지하는 규칙이 아니다. 동시 등록으로 사전 검사 이후 새 겹침이 생길 수 있으므로 기존 위반 전체 조회도 제공해야 한다.

위반 전체 조회는 인증된 사용자의 `employee_role`에 `MANAGEMENT` 권한이 있는 경우에만 서버에서 허용한다. 일반 직원·미인증 사용자는 조회할 수 없고, 요청 파라미터로 보낸 사번이나 화면의 버튼 숨김으로 권한 검사를 대신하지 않는다.

현재 앱에는 투입 등록·수정 경로와 로그인·권한 처리가 없다. 이번 변경은 ERD·DDL·실행 가능한 조회 SQL·데모 데이터·테스트를 추가하며, 등록 사전 경고와 인증 기반 조회 제한은 후속 서버 구현 요구사항이다. 위반 조회 HTTP 엔드포인트를 공개하지 않는다.

구현 책임: authenticated authorization/application transaction
