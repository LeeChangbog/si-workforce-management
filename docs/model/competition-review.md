# 경쟁 발주처 확장 독립 검토

검토일: 2026-11-06

이 검토는 경쟁 발주처 엔터티 1개, 식별 관계 2개, 기간 위반 탐지 SQL과 시연·성능 계획의 범위를 대조한다. 화면 조작과 컴퓨터 유즈를 사용하지 않았으며, 앱 인증·쓰기 기능이 없는 현재 구현 상태를 기준으로 판단한다.

## 기준과 현재 검토 상태

- 기준 커밋: `475bd5790875a317006912febdd5186a2b894160`.
- 기준 모델: 루트 엔터티 20개, 서브타입 5개, 일반 관계 26개.
- 기준 V1: 테이블 25개, FK 31개. `uk_project_employee UNIQUE (project_id, employee_id)`가 이미 존재한다.
- `docs/model/schema.json`과 `docs/erd/model-definition.json`의 기준 내용은 동일하다.
- 확장 후 예상 구조: 루트 21개 + 서브타입 5개 = 테이블 26개, 일반 관계 28개, SQL FK 33개.
- 논리 명세·경계조건과 최종 산출물을 독립 대조했다. 기존 구조의 보존, 신규 범위 일치, 실제 테스트 결과는 아래에 기록한다.

## 추가 구조 대조 기준

| 대상 | 요구와 검토 기준 |
|---|---|
| 신규 엔터티 | `CLIENT_COMPETITION` 1개 |
| 키와 참조 | `client_id_a BIGINT NOT NULL`, `client_id_b BIGINT NOT NULL`, 복합 PK `(client_id_a, client_id_b)`. 두 컬럼은 각각 `client(client_id)`를 참조 |
| 관계 역할 | CLIENT → CLIENT_COMPETITION의 `경쟁기준`, `경쟁상대` 두 식별 관계 |
| 참여 조건 | 한 경쟁관계는 A와 B를 각각 정확히 1개 필수 참조. 한 발주처는 각 역할의 경쟁관계 0..N개를 가질 수 있음 |
| 정규화된 저장 | `CHECK (client_id_a < client_id_b)`. 같은 발주처끼리의 관계와 역순 중복 저장을 거부 |
| 유효기간 | `registered_on DATE NOT NULL`, `released_on DATE NULL`, `released_on IS NULL OR released_on >= registered_on` |
| 사유 | `reason VARCHAR(200) NOT NULL` |
| 보존 범위 | 기존 25개 테이블과 26개 일반 관계의 속성·키·참조·역할을 변경하지 않음 |

`A < B`는 한 쌍을 한 방향으로만 저장하기 위한 정렬 규칙이다. 실제 조회는 경쟁 쌍의 어느 발주처 프로젝트에 먼저 투입됐는지와 무관해야 한다. 두 참조 역할은 저장 위치를 구별하며, 중복된 역방향 행을 요구하지 않는다.

## 기간 탐지 SQL 검토

### 탐지 대상과 전제

동일 사원의 직무수행이력 두 개가 서로 다른 경쟁 발주처의 프로젝트에 속하고, 두 투입 기간과 경쟁 유효기간이 공통 날짜를 갖는 경우를 검출한다. 기존 `assignment_history`는 시작·종료일이 모두 필수이며 `assigned_to >= assigned_from`을 검사한다. 경쟁관계에도 유효한 등록·해제 기간 제약을 둔다.

명세의 기간 조건은 다음과 같다.

```sql
ha.assigned_from <= hb.assigned_to
AND hb.assigned_from <= ha.assigned_to
AND cc.registered_on <= LEAST(ha.assigned_to, hb.assigned_to)
AND (
    cc.released_on IS NULL
    OR cc.released_on >= GREATEST(ha.assigned_from, hb.assigned_from)
)
```

유효한 DATE 폐구간이라는 위 전제에서 이 조건은 세 기간의 공통 교집합 존재 여부를 올바르게 판정한다. `released_on IS NULL`은 종료 제한이 없는 것으로 해석한다. 동일 날짜의 시작·종료가 맞닿으면 1일간 겹치는 것으로 포함한다. 현재 날짜 조건을 임의로 추가하면 과거 위반 조회나 미래 투입 사전 검토의 의미가 바뀌므로 명세에 없는 `CURRENT_DATE` 필터를 추가하지 않는다.

### 발주처 순서와 프로젝트 순서는 별개

`project_a.client_id = cc.client_id_a`와 `project_b.client_id = cc.client_id_b`로 조인하면 경쟁 쌍의 방향은 이미 정해진다. 이 상태에서 `project_a.project_id < project_b.project_id` 또는 `ha.assignment_id < hb.assignment_id`를 중복 제거 조건으로 추가하면 실제 위반을 누락할 수 있다. 프로젝트·이력 ID의 발급 순서와 발주처 ID의 정렬 순서는 독립적이기 때문이다.

서로 다른 발주처의 프로젝트를 각각 조인하므로 동일 프로젝트를 자기 자신과 비교하는 결과는 원천적으로 제외된다. A/B를 바꿔 조인한 역방향 행을 별도로 UNION할 필요도 없다.

### 명세의 출력 기간과 실제 위반 기간

사용자 지정 출력은 다음과 같이 두 투입 기간만의 교집합이다.

```sql
overlap_from = GREATEST(ha.assigned_from, hb.assigned_from)
overlap_to   = LEAST(ha.assigned_to, hb.assigned_to)
```

이 값은 WHERE에서 경쟁관계의 유효성을 확인한 뒤 출력하는 **투입 기간 겹침**이다. 경쟁 등록·해제일로 잘라낸 실제 위반 기간과 다를 수 있다. 예를 들어 두 투입의 교집합이 3월 1~31일이고 경쟁 등록일이 3월 20일이면 명세 출력은 3월 1~31일이며, 경쟁 상태에서의 실제 겹침은 3월 20~31일이다.

최종 SQL은 요청된 `overlap_from/to` 의미를 유지해야 한다. 이후 실제 위반 기간을 화면에 표시하려면 별도 이름을 사용해 `GREATEST(ha.assigned_from, hb.assigned_from, cc.registered_on)`과 경쟁 해제일을 함께 고려한 종료일을 계산한다. 명세 컬럼을 조용히 다른 의미로 바꾸지 않는다.

### 여러 직무 이력에 따른 중복

한 프로젝트참여에 여러 직무수행이력이 존재할 수 있으므로, 한 사원의 같은 프로젝트 쌍이 여러 이력 조합에서 검출될 수 있다. 이 결과는 반드시 같은 DB 행의 잘못된 중복은 아니다. 명세 출력이 이력별 투입 시작·종료를 포함하므로 기본 단위는 ‘투입 이력 조합’으로 설명한다. 출력값이 완전히 같은 행을 제거하는 `DISTINCT`와, 여러 겹침 구간을 하나로 합치는 프로젝트 단위 집계는 서로 다른 처리다. 후자의 집계를 구현한 것으로 주장하지 않는다.

## 경계 사례와 기대 결과

| 사례 | 기대 결과 |
|---|---|
| 같은 사원이 경쟁 발주처 두 곳의 프로젝트에 공통 유효기간 동안 투입 | 검출 |
| 두 투입의 종료·시작이 같은 날짜이고 그 날짜에 경쟁관계 유효 | 1일 겹침으로 검출 |

| 두 투입은 겹치지만 공통 기간이 경쟁 해제일 다음 날 시작 | 미검출 |
| 경쟁 등록일이 두 투입 공통 기간의 마지막 날과 같음 | 검출 |

| 서로 다른 사원 또는 경쟁관계가 없는 발주처 | 미검출 |
| A측 프로젝트 ID가 B측보다 크지만 발주처 A < B이고 기간은 겹침 | 검출. 임의 프로젝트 ID 정렬 조건으로 제외하면 안 됨 |
| A = B, A > B, 존재하지 않는 발주처 | CHECK 또는 FK로 등록 거부 |
| 해제일 < 등록일 | CHECK로 등록 거부 |
| 이미 저장된 동일 `(A,B)`를 다른 유효기간으로 INSERT | 복합 PK에 의해 거부 |

## 동일 경쟁 쌍 재등록 제약

복합 PK가 `(client_id_a, client_id_b)`뿐이므로 한 쌍에 한 행만 존재할 수 있다. 관계를 해제한 후 같은 두 발주처가 다시 경쟁하게 된 경우 별도 행을 추가할 수 없다. 기존 행의 등록·해제일을 덮어쓰면 첫 번째 경쟁기간 이력이 사라져 과거 위반 판정이 달라진다.

이번 확장은 요청한 키와 엔터티 수를 그대로 유지하며, 반복 등록 이력은 지원하지 않는 범위로 명시한다. 이력을 지원하려면 향후 키에 회차/시작일을 포함하거나 별도 기간 이력을 설계해야 하므로 이번 작업에서 임의 확장하지 않는다.

## 권한·사전 경고와 API 범위

현재 앱은 홈 조회와 health를 제공하며 회원가입·인증·쓰기 서비스가 없다. 따라서 다음을 구분해야 한다.

- 경쟁 발주처 등록 시 사전 경고, 기존 위반 조회, 경영진 전용 조회는 업무 규칙과 시연 SQL로 설계한다.
- `MANAGEMENT` 권한은 기존 `access_role`·`employee_role` 모델을 활용하는 후속 서버 권한 검사에 연결한다.
- SQL 파일 이름·주석에 ‘경영진용’이라고 적거나 요청 파라미터의 사번을 믿는 것만으로 접근 통제가 구현되지는 않는다.
- 인증이 없는 공개 조회 API를 추가하면 경영진 전용이라는 요구와 충돌한다.

이번 핵심 과제 범위가 ERD 확장·DDL·탐지 SQL·테스트 데이터라면 새 REST API는 필수가 아니다. 기존 앱의 등록·권한 체계를 함께 구현하지 않고 API만 추가하기보다, 서버 기능은 후속 구현으로 명시하고 해당 구현 완료를 주장하지 않는 것이 현실적인 범위다.

## 테스트 데이터와 성능 계획 검토

- 경쟁 쌍은 A < B를 만족하는 2~3개, 위반 투입 사례는 기대 결과를 셀 수 있는 2~3개를 준비한다.
- 음성 사례로 비경쟁 쌍, 다른 사원, 기간 비중첩 또는 경쟁 유효기간 밖 사례를 포함하면 탐지 조건을 검증하기 쉽다.
- A측 프로젝트 ID가 더 큰 양성 사례는 잘못된 프로젝트 ID 정렬 조건으로 인한 누락을 탐지한다.
- 실제 사원 식별정보 대신 가상 데이터를 사용하며 시연 데이터와 성능 측정용 대량 데이터를 구분한다.
- 성능 계획의 후보는 `project(client_id)`, `assignment_history(participation_id, assigned_from, assigned_to)`다. 요청한 `project_participation(project_id, employee_id)` 경로는 기존 `uk_project_employee` UNIQUE 인덱스를 활용할 수 있으므로 같은 열·순서의 일반 인덱스를 중복 추가할 필요가 없다.
- 수만 건 이력에 같은 결과를 반환하는 쿼리를 대상으로 통계 갱신 후 인덱스 전후 `EXPLAIN ANALYZE`와 여러 차례 실행 시간을 비교한다. 첫 실행·반복 실행의 캐시 차이와 측정 환경을 함께 기록한다.
- 인덱스가 모든 실행에서 사용되거나 일정 시간 이상 개선된다고 보장하지 않는다. 이번 산출물은 측정 **계획**이며 실제 성능 개선 수치·실험 완료를 보고하지 않는다.

## 기존 구조 보존과 마이그레이션 경계

사용자가 V1에 직접 추가하도록 요청한 범위에 따라, 기존 25개 CREATE TABLE과 제약을 보존한 채 신규 테이블만 추가하는 새 DB용 DDL을 검토한다. 이미 V1이 적용된 영속 DB에서는 본문 추가도 Flyway checksum을 변경한다. 기존 DB에 그대로 재적용 가능하거나 자동 업그레이드된다고 표현하면 안 된다. 이번 작업에서 migration repair나 기존 데이터 변경을 수행하지 않는다.

최종 독립 비교 항목은 다음과 같다.

1. 기준 V1의 기존 25개 CREATE TABLE·제약 본문이 그대로 유지되는지.
2. 신규 CREATE TABLE은 `client_competition` 하나이며 PK 1개·CLIENT로의 FK 2개·요청 CHECK 2개가 있는지.
3. 두 JSON 모델의 기존 엔터티·서브타입·관계 정의가 보존되고 신규 엔터티 1개·식별 관계 2개만 추가되는지.
4. 도면에서 역할이 구분된 두 식별 관계와 부모 1 / 자식 0..N 표기가 존재하는지.
5. SQL 출력·조건·정렬, 시연 데이터 수와 기대 결과, 권한 및 성능 계획의 구현 상태 설명이 명세와 일치하는지.

기간 경계, 재투입 공백, 발주처 A측의 더 큰 프로젝트/이력 ID, 겹침 출력의 비절단 의미가 테스트에 포함돼 있다. 실제 확인한 테스트 환경은 H2 PostgreSQL 호환 모드다. 위 결과만으로 PostgreSQL에서 대량 데이터 성능 실험을 완료했거나 앱 권한 통제를 구현했다고 해석하지 않는다.

필수 구조·SQL·산출물 범위에서 미해결 결함은 발견하지 않았다. 동일 경쟁 쌍의 재등록 이력 미지원, 기존 영속 DB의 V1 checksum 변경, 후속 권한·사전 경고 구현은 앞서 명시한 제한으로 남는다. Native CHECK는 엔터티 설명·메타데이터에 기록하며 실제 강제는 SQL V1이 담당한다. 기존 native UNIQUE 조회 한계는 이번 변경과 별개이며 기존 감사 기록을 따른다.

추가 확인: native 모델 설명의 이전 합계 표기는 해결됐다. 최신 `after-export.json`의 `ModelDesc`에서 루트 21개·하위 유형 5개·일반 관계 28개를 확인했다. 갱신 스크립트는 저장 후 파일을 닫고 다시 열어 기존 구조, 신규 5개 속성, 신규 두 관계의 스냅샷을 재대조하며, 최신 감사 기록의 `saved_file_reopened_verified`도 참이다.
